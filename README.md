# QBoard — Internal MyStackOverflow

A **Q&A platform** for teams: ask questions, get answers from colleagues, and eventually **AI-generated answers** (local model or cloud service), clearly labeled as such.

Built as part of the **Liga ACLabs × Haufe** collaboration.

---

## Vision

| Feature | Status |
|---------|--------|
| Question list with tags, votes, Open/Solved status | ✅ Implemented (mock) |
| Detail page: description, answers, comments | ✅ Implemented (mock) |
| Authentication (sign in / sign up) | 🟡 UI + mock hook; not fully wired |
| Posting new questions / answers | ⏳ Planned |
| **AI companion** — generate an answer for a question | ⏳ Planned |
| Backend + real API | ⏳ Planned |

The data model already includes fields for the future AI flow:

- `allow_ai_companion` on a question — whether the AI companion is allowed
- `is_ai_generated` on an answer — whether the answer was generated by AI

The AI companion will be able to run **locally** (Ollama) or via an **external API** — integration details to follow.

---

## How this project was built

This app **is not a one-shot generated dump**. It was built **step by step**, with AI tools (e.g. Cursor) as assistants, but with **understanding first**: types, routing, components, and mock data are chosen and reviewed deliberately.

In short:

- each piece (page, hook, type) has a clear role in the architecture;
- mock data mirrors the shape the real API will have;
- auth lives in a separate hook, ready to wire into the UI;
- AI in the product is **planned**, not bolted on without a data model.

---

## What works today

- **Home** (`/`) — question list from `mockData.ts`, clickable cards
- **Question details** (`/question/:id`) — description, tags, comments, answers (including Accepted / AI Generated badges)
- **Sign in / Sign up** (`/sign-in`, `/sign-up`) — forms; real session logic lives in `useAuth`, not yet connected to the forms
- **Navbar** — QBoard branding, links to auth

Everything runs **without a backend** — static data in the frontend.

## Supabase

The frontend uses the [Supabase JS client](https://supabase.com/docs/reference/javascript/introduction) for auth, database, and storage (as you wire features in).

### Setup

1. Create a project at [supabase.com](https://supabase.com).
2. Copy `smo-frontend/.env.example` to `smo-frontend/.env`.
3. Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` from **Project Settings → API** (use the anon / publishable key, not the service role key).

Restart the dev server after changing `.env`.

### Usage

Import the shared client anywhere:

```ts
import { supabase } from './lib/supabase'

const { data, error } = await supabase.from('questions').select('*')
```

Client singleton: `smo-frontend/src/lib/supabase.ts`.

## Quick start

### Requirements

- [Node.js](https://nodejs.org/) 18+ (20+ recommended)
- npm

```bash
cd smo-frontend
cp .env.example .env   # then fill in your Supabase keys
npm install
npm run dev
```

Open the URL shown in the terminal (usually `http://localhost:5173`).
